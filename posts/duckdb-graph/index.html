DuckDB 图计算：人际关系连通分量三种实现

2026-03-26 — DuckDBGraphSQLOnagerDuckPGQ

社交关系天然是一张图：A 认识 B，B 认识 C，则 A 与 C 虽无直接边，也同属一个圈子。把「能通过认识关系串起来的人」收成一组，本质就是无向图上的连通分量（Connected Components）。

本文用同一套样例数据，对比三种在 DuckDB 内落地的做法：纯 SQL 递归合并、Onager 连通分量、DuckPGQ 弱连通分量。

业务场景

Section titled “业务场景”

问题描述

Section titled “问题描述”

两张表：

表字段含义
personperson_id, display_name人员主数据
knowsperson_a, person_b, relationship_type认识关系；friend 可信，unknown 忽略

规则：

  1. 每条可信的 knows 记录是一条无向边（A 认识 B 等同于 B 认识 A）。
  2. 传递闭包：A→B、B→C 则 A、B、C 同一圈子。
  3. relationship_type = 'unknown' 不参与构图；没有任何可信边的人（孤立点）不输出。
  4. 输出：display_name、person_id、group_id、该圈子完整 all_members。

解决方案

Section titled “解决方案”

三种方案解决的是同一个图问题，只是「如何求连通分量」不同。

方案一：递归 CTE 列表合并

Section titled “方案一：递归 CTE 列表合并”

思路：每条认识关系先变成两人集合，再在递归 CTE 里用 list_has_any 做重叠合并，直到集合不再变大——即「集合相交」语义下的传递闭包。

要点：

  • seed：每条 friend 边 → 排序后的两人列表。
  • 递归步：当前圈子与另一条边集合有交集、但尚未完全包含时，合并扩圈。
  • QUALIFY ... ORDER BY member_count DESC：每人只保留最大合并结果。
  • 零扩展依赖，适合环境受限、圈子不大的场景。

方案二：Onager 连通分量

Section titled “方案二：Onager 连通分量”

Onager 是 DuckDB 社区图算法扩展。节点 ID 需为 BIGINT，因此先把 person_id 映射成数字，再调 onager_cmm_components。

要点：

  • 边直接来自 knows，无需自连接；Onager 默认按无向处理 src/dst。
  • HAVING len(...) > 1：过滤单人分量，与方案一对齐。
  • API：onager_cmm_components((SELECT src, dst FROM edges)) → (node_id, component)。

方案三：DuckPGQ 弱连通分量

Section titled “方案三：DuckPGQ 弱连通分量”

DuckPGQ 提供 SQL/PGQ 属性图与图算法。先声明 PROPERTY GRAPH，再调用 weakly_connected_component（弱连通分量，边方向忽略——正适合「认识」这种双向语义）。

DuckPGQ 对 DuckDB 版本有兼容矩阵要求；DuckDB 2.0+ 需 SET active_grammar_extensions = ['duckpgq'] 才能解析 CREATE PROPERTY GRAPH。

要点：

  • 点表只收录出现在可信边上的人；边端点必须落在点表内。
  • LABEL Knows 供算法与后续 GRAPH_TABLE 模式匹配复用。
  • weakly_connected_component 参数为图名、点标签、边标签（字符串）。

对比

Section titled “对比”

三种方案在样例上得到同一组圈子（Alice–Dave 与 Eve–Frank）；差异在依赖、写法与扩展性。

怎么选

Section titled “怎么选”
  • 无扩展权限、逻辑一次性：递归 CTE。
  • 只要连通分量、易做成数值边表：Onager，代码最短。
  • 还要写认识路径、共同好友、多算法：DuckPGQ，一次建图多次复用。

实现时注意

Section titled “实现时注意”
  1. 无向语义要一致：三种方案都按无向处理「认识」；若业务是单向关注，需改用有向连通 / 强连通，算法与边表都不同。
  2. 过滤条件对齐：一律只用 relationship_type = 'friend'，漂移会导致圈子分裂或误并。
  3. 孤立点：Grace 仅有 unknown 边，三种写法都不会进入输出。
  4. group_id 稳定性：DENSE_RANK() OVER (ORDER BY all_members) 依赖列表排序；换序会改编号，成员集合不变。

小结

Section titled “小结”

「A 认识 B、B 认识 C」是典型的无向连通分量问题。DuckDB 既可以纯 SQL 递归完成，也可以通过 Onager / DuckPGQ 用标准图算法表达；选型取决于环境约束与是否还要继续做图分析。同一套样例下三种写法结果对齐，可作为换成真实社交边表的对照基线。
